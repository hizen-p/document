# OutputFormat：通用输出格式规范

> 规范定位：格式层模块
>
> 本规范仅负责约束输出格式、内容组织、表达方式和文档质量。
> 不负责定义具体任务目标，也不替代用户提供的任务提示词。
>
> 本规范是所有提示词工程输出的格式主标准之一。各提示词中与本规范冲突的格式约定一律失效，以本规范为准。

## 0. 输出位置强制规则与模块化说明

所有最终输出的文档必须输出到 `./docs/` 目录下。

禁止：

- 将输出文档写到 `./docs/` 以外的目录。
- 在提示词中规定其他输出根目录（如 `project_analysis/` 等）。

各提示词可以在 `./docs/` 下组织子目录结构，但根目录必须是 `./docs/`。

为控制核心规范体积，Mermaid 图表详细规则拆分到独立文件 `MermaidRules.md`。本文件只保留核心铁律，详细规则以该模块文件为准。

## 1. 适用范围与职责边界

本规范作为可组合的输出格式模块使用，应与其他任务提示词配合使用。

适用场景包括：技术分析、工程问题排查、项目文档编写、知识整理、代码与配置说明、学习资料整理、方案设计与对比。

本规范不负责：自行确定用户未提出的任务目标、擅自扩大任务范围、替代系统指令或用户明确要求、在缺少依据时编造事实。

## 2. 指令优先级与冲突处理

指令优先级从高到低：系统指令 > 开发者指令 > 用户明确要求 > 任务专用提示词 > 本输出格式规范 > 一般性建议。

当不同规则发生冲突时，遵循优先级更高的指令，优先满足用户对输出内容和格式的明确要求，不得为了满足本规范而违反任务要求。

## 3. 总体输出原则

输出应满足：准确、清晰、完整、可读、可执行、可验证、可维护。

根据任务复杂度选择输出形式，不强制所有回答都使用完整章节结构。

## 4. 输出范围与文件规则

除非任务另有要求：

- 只输出与当前任务相关的内容
- 不擅自创建额外文档
- 需要生成文档时，必须输出到 `./docs/` 目录下
- 文件名应具有明确含义，建议使用英文、数字、短横线或下划线
- 不覆盖已有文件，除非用户明确授权
- 不声称已经创建、修改或验证不存在的文件

## 5. 文档结构规范

复杂文档可采用：标题 → 背景与目标 → 前置条件 → 核心内容 → 操作步骤 → 示例 → 注意事项 → 验证方法 → 问题排查 → 总结。

不要求每份文档都包含以上全部章节。章节应层级清晰、避免过深、避免重复、标题准确。

## 6. 信息表达与可信度

应明确区分：已确认事实、用户提供的信息、合理推断、待确认信息、建议方案、假设示例。

禁止：将推测描述为确定事实、将示例路径描述为真实路径、将未执行的命令描述为已执行、隐瞒重要限制条件。

### 不确定性状态表

| 状态 | 含义 |
| --- | --- |
| 已确认 | 有直接代码、配置或运行证据 |
| 高可信推断 | 多个证据共同支持，但尚未完全验证 |
| 推断 | 根据结构、命名、调用关系等推测 |
| 待验证 | 可以通过运行、测试或实验确认 |
| 未知 | 当前资料无法判断 |
| 未发现 | 当前扫描范围内没有找到相关实现 |

不得将"推断"改写成"事实"，不得将"未发现"改写成"不存在"，不得将"待验证"改写成"已完成"。

## 7. Markdown 基础规范

### 7.1 标题

使用 `#` 至 `######` 表示标题层级，层级连续合理，不使用大量符号代替标题。

### 7.2 列表

无序列表用 `-` 或 `*`，有序列表用 `1. 2. 3.`。步骤有先后关系时用有序列表，并列信息用无序列表。

### 7.3 强调

`**粗体**` 用于重点概念或关键结论，`` `行内代码` `` 用于命令、变量、函数、文件名和路径。避免滥用粗体和装饰符号。

## 8. 表格规范

只有在表格能提高信息对比效率时才使用。表格应有明确表头、列含义一致、单元格内容不过长。

## 9. 代码、命令与配置规范

### 9.1 代码块

代码块必须标注语言类型。常见语言标记：`c`、`cpp`、`python`、`bash`、`shell`、`json`、`yaml`、`makefile`、`text`。

### 9.2 命令与命令输出分离

命令用 `bash` 块，命令输出用 `text` 块：

```bash
ls -l /dev
```

```text
crw-rw---- 1 root audio 116, 0 snd
```

### 9.3 路径

路径应使用行内代码。不得在没有依据时编造项目路径、设备节点或配置文件。

### 9.4 代码说明

涉及代码时，应说明代码作用、关键逻辑、输入输出、依赖条件、编译或运行方法、常见错误、验证方式。

### 9.5 配置样例

配置样例优先使用实际配置格式（YAML、JSON、INI、XML 等）。不得为了格式统一而改变原始配置语义。

## 10. 机器可解析格式

输出 JSON、YAML、XML 时：保证语法有效、不在代码块中混入无关解释、字段命名一致、不添加格式标准不支持的注释。

当用户明确要求纯 JSON 时，不要在主体数据前后添加额外说明。

## 11. Prompt、XML 与原始文本

需要被其他模型、程序或工具直接读取的内容，应保留原始结构，使用代码块保护特殊符号。

## 12. Mermaid 与图表

架构图、流程图、模块关系、依赖关系、数据流、状态机和时序关系优先使用 Mermaid。

### 核心规则

1. 使用 `graph` 而非 `flowchart`。
2. 知识地图优先 `graph LR`（横向）；流程、调用链、生命周期优先 `graph TD`（纵向）。
3. 节点标签和消息文本中**禁止** HTML 换行标签、Unicode 箭头（`→` `←` `↑` `↓`）、中文标点（`，` `：` `。` `；`），需要分隔时用空格。
4. 以 `/` 开头的节点文本必须用双引号包裹（如 `A["/proc/device-tree/"]`）。
5. 禁止使用图片承载架构图、流程图、数据流、依赖关系、状态机、时序关系。

详细规则（图表类型选择、连线规范、时序图/状态图专项、节点文本规范、代码块嵌套、渲染失败 13 步排查、替代方案、大图拆分等）见 `MermaidRules.md`。

### 图表原则

Mermaid 必须服务于理解，不得为了"看起来专业"而强行绘制。每张图只表达一个主要问题。

> **图负责建立结构，文字负责解释结构。**

## 13. 公式规范

涉及数学公式时，根据复杂度选择行内公式或独立公式。符号定义清晰，变量含义明确，避免没有上下文的复杂公式。

## 14. 证据、引用与来源

涉及外部事实、版本信息、标准、数据或具体结论时，应提供来源。优先使用官方文档、项目源码、内核文档、芯片厂商资料、标准规范。

不伪造链接、引用或参考资料。无法确认来源时应明确说明。

## 15. 工程路径与 Markdown 链接

项目路径应保持原样，不随意修改。

### VSCode 可跳转的代码路径

- **文件路径**（需要可跳转）：使用 Markdown 链接，链接地址为相对项目根目录的路径。

  ```markdown
  [src/video/camera.c](src/video/camera.c)
  ```

- **函数 / 变量 / 宏 / 结构体 / API 名称**（仅展示）：使用行内代码。

### 跳转链接规则

1. 链接地址使用相对项目根目录的真实路径。
2. 指向具体行或行范围时，使用 `#L` 锚点：`[src/video/camera.c#L120-L145](src/video/camera.c#L120-L145)`。
3. 路径必须真实存在。无法确认时回退为行内代码并标注【信息不足】。
4. 文档输出到 `./docs/`，链接路径仍以项目根目录为基准，不要写成相对 `./docs/` 的路径。
5. 表格中引用文件路径时同样使用 Markdown 链接。

## 16. 内容组织与可维护性

分析类任务：先结论再原因；实践类：先前提再步骤；学习类：先概念再应用；对比类：先差异再场景；排查类：先现象再原因和验证。

避免：重复相同结论、无目的地扩展背景、添加大量无关知识、过度拆分章节、使用复杂格式掩盖内容不足。

## 17. 禁止项

禁止：编造事实/数据/命令执行结果、编造不存在的文件/目录/链接、将猜测当作已确认事实、擅自扩大任务范围、重复输出相同内容、使用过度复杂的格式、将内部推理过程/Chain of Thought/工具调用过程混入最终交付内容。

## 18. 最终质量检查

输出前检查：

- [ ] 是否满足用户的核心要求
- [ ] 是否遵循更高优先级的指令
- [ ] 是否存在无依据的事实或结论
- [ ] 是否区分事实、推断和建议
- [ ] 代码、命令和配置是否格式正确
- [ ] 文件路径和链接是否有依据
- [ ] 标题层级是否合理
- [ ] Mermaid 或公式是否有效
- [ ] 是否存在明显重复内容
- [ ] 是否可以进一步简化

## 19. 最小输出原则

在满足任务要求的前提下，使用足够但不过量的格式。

简单问题直接回答；多步骤任务用列表；内容对比必要时用表格；复杂分析用章节结构；代码任务用代码块；机器读取任务遵循目标格式。

不要为了套用规范而强行使用表格、流程图、公式或完整章节。

## 20. 规范生效说明

本规范是可组合的输出格式层，应与具体任务提示词共同使用。

任务要求优先于默认格式，内容准确性优先于形式完整性，清晰易读优先于复杂排版，可验证性优先于主观判断，必要性优先于格式堆叠。

# 项目输入识别工作流

## 输入输出契约

- 前置条件：用户提供的任意项目相关信息
- 产出物：输入类型判定、信息完整度状态（完整 / 部分信息 / 信息不足）
- 消费者：workflows/01_repository_check.md

---

## 目标

识别用户提供的信息类型。

---

## 输入分类

判断输入属于：

1. 仓库链接
2. 项目名称
3. 项目简介
4. README
5. 源码目录
6. 源码文件
7. 项目附件

---

## 信息完整度

检查：

- 是否知道项目名称
- 是否知道项目来源
- 是否能访问源码
- 是否有 README
- 是否有构建信息

---

## 输出状态

完整：

可以继续。

部分信息：

继续基础分析，但明确限制。

信息不足：

要求补充。

---

## 禁止

禁止：

根据项目名称直接假设：

- 使用什么语言
- 有什么目录
- 有什么架构
- 有什么函数

---

## 边界情况处理

### 私有仓库 / 无法访问

处理：

1. 明确告知用户仓库无法访问
2. 如果用户能提供源码包或 README，转为离线分析模式
3. 无法获取任何资料时，终止分析并说明原因

### 项目为空 / 仅有 README

处理：

1. 仅分析 README 可提供的信息
2. 架构、调用链、数据结构等需要源码的模块全部标注【信息不足】
3. 在 project_index.md 中标注为"仅文档分析"

### 仅有二进制 / 无源码

处理：

1. 不进行源码级分析
2. 仅分析可观察的行为（如命令行参数、输出格式）
3. 明确告知用户源码缺失，分析深度受限

### 恶意项目 / 可疑项目

处理：

1. 不执行项目代码
2. 仅做静态结构分析
3. 在 repository_check 中标注风险，建议用户谨慎

### 项目名称重复 / 多个同名仓库

处理：

1. 要求用户确认具体仓库（提供完整 URL 或作者+名称）
2. 未确认前不假设是哪一个

### 超大项目（超过 1000 文件）

处理：

1. 严格遵循 workflows/03_analysis_planning.md 的超大型项目策略
2. 第一批只输出项目地图和索引，不深入源码
3. 每批分析前更新 project_index.md 的分批计划

# 质量自检清单

本规则定义每个分析阶段的完成标准和质量门槛。
每个阶段输出前必须自检。

---

## 通用质量门槛

所有阶段必须满足：

1. 每个核心结论都有【证据】标注
2. 无证据的项使用【信息不足】或【推测】标记
3. 不存在编造的文件、函数、调用链
4. 重要度标签格式统一为【重要度：N｜语义】

---

## 输出格式门槛

输出格式（Markdown 标题层级、分割线、代码块语言声明、禁止 HTML/SVG、禁止图片公式/表格/流程图、LaTeX 公式、原生 Markdown 表格等）以及 Mermaid 语法合规性（使用 `graph` 而非 `flowchart`、方向选择、禁止 HTML 换行标签、禁止 Unicode 箭头、禁止中文标点、特殊字符双引号包裹等）统一遵循 `output_format/OutputFormat .md` 的规定。

本清单不再重复上述通用格式规则，仅保留本 Skill 专属的完成标准。

---

## 阶段完成标准

### 00 project_intake 完成标准

- 已判定输入类型
- 已给出信息完整度状态（完整 / 部分信息 / 信息不足）
- 信息不足时已明确要求用户补充什么

### 01 repository_check 完成标准

- 检查结果表 8 项全部填写（存在 / 官方 / Fork / 源码完整性 / README / 构建说明 / Release / 维护状态）
- 每项都有证据
- 已给出最终判断（推荐学习 / 可以学习但需注意 / 不建议作为主要学习对象）

### 02 domain_identification 完成标准

- 已输出主领域、子领域、核心用途、运行环境
- 领域判断有依据（源码 / README / 构建配置）
- 已给出置信度（高 / 中 / 低）

### 03 analysis_planning 完成标准

- 已评估项目规模（小 / 中 / 大 / 超大）
- 已生成分析策略
- 大型项目已生成分批计划
- 已生成 project_index.md

### 04 pre_check 完成标准

- 已输出技能门槛（必备 / 建议 / 高级 / 零基础可行性 / 学习难点）
- 已输出硬件前提（无证据时不编造性能指标）
- 已输出系统环境、软件依赖、项目风险
- 已引用 01、02 的结论，未重复执行

### 05 quick_verify 完成标准

- 已给出最小构建环境
- 已给出编译部署步骤（优先官方）
- 已给出最小 Demo 的输入→执行→预期输出→成功判断
- 已列出常见错误及解决方法（如存在）

### 06 depth_analysis 完成标准

- 已定位程序入口（文件 + 函数）
- 已画出初始化流程（只保留真实步骤）
- 已追踪至少一条核心调用链（含文件、函数、输入、处理、数据变化、下一模块）
- 已分析核心数据结构及生命周期
- 已给出源码阅读路线
- 模块依赖有源码或构建证据，非猜测

### 07 domain_analysis 完成标准

- 已加载正确的领域 Profile
- 存在的专项模块已分析（含全局总览、实现位置、工作流程、证据、置信度）
- 不存在的专项模块已明确标注"本项目无相关内容"
- 未因 Profile 存在而假设项目一定有某能力

### 08 learning_map 完成标准

- 8 个阶段都有学习目标和完成标准
- 已给出推荐源码阅读顺序
- 已列出必须追踪的调用链
- 已指出当前阶段不要浪费时间的内容
- 已给出进阶方向

---

## 最终自检

全部阶段完成后，检查：

- [ ] project_index.md 的文档索引中 5 个分析文件状态已更新
- [ ] project_index.md 的「无法确认」小节已汇总所有【信息不足】项
- [ ] 所有调用链都有源码证据
- [ ] 所有硬件/性能指标都有证据或标注【信息不足】
- [ ] 领域 Profile 中不存在的能力已明确标注
- [ ] 学习路线中的阅读对象都是真实存在的文件
- [ ] 所有文档输出到 `./docs/` 目录下
- [ ] Markdown / Mermaid / 代码块 / 公式 / 表格等格式符合 `output_format/OutputFormat .md` 规定

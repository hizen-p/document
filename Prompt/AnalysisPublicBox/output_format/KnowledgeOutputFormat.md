# 知识型文档输出规范

本文件是知识型文档（技术学习笔记、知识预览、技术说明、个人知识库）的详细规范。核心 OutputFormat 中只保留关键原则，详细规则以本文件为准。

---

## 一、知识型文档的表达规范

如果输出内容属于技术学习笔记、知识预览、技术说明或个人知识库，除基本 Markdown 格式外，还应遵循以下表达规范。

### 1. 独立可读

最终文档必须能够脱离当前对话独立阅读。

禁止使用：

```text
我们刚才提到……
上面那个东西……
前面已经讲过……
你刚才说的……
```

不得依赖聊天上下文才能理解内容。未来用户只打开这份 Markdown，也应该能够理解主要内容。

### 2. 信息目标优先

不要追求"信息最多"，应该追求"目标匹配度最高、知识脉络最清晰、能够帮助读者建立正确认知"。

内容应该优先回答：

```text
这是什么？
为什么存在？
解决什么问题？
位于整个体系的什么位置？
核心组成是什么？
核心概念之间是什么关系？
如何工作？
必要时如何通过代码理解？
实际在哪里使用？
后续应该继续理解什么？
```

### 3. 内容深度动态调整

禁止固定所有文档的长度和章节数量。根据内容复杂度动态调整：

```text
简单知识 → 简洁建立核心模型
中等知识 → 核心概念 + 关系 + 原理 + 示例
复杂知识 → 知识地图 + 流程 + 数据流 + 代码 + 关联知识 + 学习导航
```

目标是"刚好足够建立可靠认知"，不是"写得越长越好"。

### 4. 信息密度

避免：重复解释、无意义历史背景、搜索结果堆砌、大量原文引用、弱相关内容、不必要的高级细节、为了增加篇幅而增加章节。

每一部分都必须有明确作用。

---

## 二、知识结构表达规范

### 1. "为什么存在"优先

技术知识尽可能回答：

```text
在它出现之前有什么问题？
↓
为什么需要它？
↓
它解决什么问题？
↓
为什么设计成这样？
↓
如果没有它会怎样？
```

目标是让读者理解知识存在的原因，而不是只记住定义。

### 2. 知识脉络优先于知识罗列

不要只输出 A、B、C、D、E 的罗列。应尽可能表达真实的因果关系、依赖关系、层级关系、调用关系、数据流、控制流、生命周期、状态变化。

推荐脉络：

```text
为什么出现
    ↓
遇到了什么问题
    ↓
为什么需要它
    ↓
采用什么方案
    ↓
方案由什么组成
    ↓
各部分如何协作
    ↓
工作过程
    ↓
最终结果
```

禁止为了让文章"看起来有脉络"而制造不存在的关系。

### 3. 根据内容类型动态设计结构

不要机械套用固定模板。例如：

**驱动**：硬件 → 内核框架 → 驱动 → 设备 → 用户空间 → 数据/控制路径

**协议**：问题 → 协议目标 → 协议机制 → 消息 → 状态 → 交互流程 → 异常

**算法**：问题 → 核心思想 → 步骤 → 数据结构 → 复杂度 → 示例

**编程语言**：问题 → 设计目的 → 基本概念 → 语法 → 执行过程 → 示例

**系统架构**：整体结构 → 模块 → 模块关系 → 数据流 → 控制流 → 生命周期

如果某个章节对当前主题没有实际价值，直接删除。

---

## 三、总览图与知识地图

当内容结构较复杂时，优先提供一张整体知识地图。（Mermaid 详细规则见 MermaidRules.md）

知识地图优先使用横向展开，流程和调用链使用纵向展开。

如果一张知识地图节点过多导致字体过小，应拆分成多张小图，每张聚焦一个子主题。

---

## 四、示例代码规范

当代码能够明显帮助理解时才提供代码。

优先：最小可运行示例、最小 API 示例、关键代码片段、简化实现、用户空间与内核空间对应示例、能够直接验证某个概念的最小实验。

代码必须服务于知识理解，而不是展示代码量。不要默认生成几百行完整项目。

### 代码与正文必须对应

每个重要代码示例都应该说明：

1. 它做什么
2. 它位于知识结构的哪个位置
3. 为什么需要这一步
4. 执行后发生什么
5. 关键 API / 数据结构分别对应什么概念

推荐结构：

```markdown
### 示例：打开字符设备

下面的代码对应"用户空间通过 open() 进入字符设备驱动"的过程。

```c
int fd = open("/dev/example", O_RDWR);
```

这里的 open() 是用户空间入口，后续会进入内核中的文件操作路径。
```

代码与正文必须形成明确对应关系。

---

## 五、术语规范

专业术语第一次出现时，尽可能提供：中文名称、英文名称、缩写、一句话解释、当前知识中的作用。

例如：

```markdown
> 字符设备（Character Device，Char Device）是 Linux 中用于以字符流方式访问设备的一类设备抽象。
```

之后可以直接使用简称。不要在每次出现术语时重复定义。

---

## 六、直觉理解与严格定义

对于复杂概念，可以同时提供：

### 直觉理解

帮助读者快速建立模型。

### 严格理解

确保技术准确。

两者不能互相替代。

如果使用类比，必须明确："类比只是辅助理解，不等价于真实机制。"如果类比可能造成错误认知，必须指出类比边界。

---

## 七、常见误区

只有确实存在高概率误解时才加入。

推荐结构：

```text
错误理解
↓
为什么容易这样理解
↓
正确理解
```

例如：

```markdown
### 常见误区

**错误理解：** /dev/video0 就是摄像头硬件本身。

**为什么容易这样理解：** 用户通常通过该路径访问摄像头。

**正确理解：** /dev/video0 是用户空间访问 V4L2 视频设备的设备节点，背后还涉及驱动、设备对象以及硬件。
```

不要为了凑章节而制造"常见误区"。

---

## 八、实际应用规范

如果知识具有工程价值，应说明它通常在哪里出现。

例如：

```text
用户程序
    ↓
/dev/xxx
    ↓
内核驱动
    ↓
硬件
```

可以适当连接真实工程场景，但必须保持主题边界。不要因为一个知识点与其他技术有关，就无限扩展到所有相关技术。

---

## 九、相关知识连接

指出当前知识与其他知识的关系。

例如：

```text
Linux 字符设备
├── VFS
├── Driver Model
├── sysfs
├── udev
├── ioctl
└── 用户空间系统调用
```

相关知识只做必要解释。不要自动把每个关联知识展开成新的学习主题。

如果某个关联知识只需要知道"它存在"，可以只做索引：

```markdown
- DMA：后续学习高速数据传输时进一步理解。
- IOMMU：后续学习设备地址转换时进一步理解。
```

---

## 十、学习导航与后续行动

对于学习型或知识预览型文档，结尾可以提供：

### 正式学习时重点关注

列出读者后续真正应该重点理解的问题。例如：

```text
1. 为什么需要 major / minor？
2. cdev 和设备节点是什么关系？
3. file_operations 如何连接用户空间和驱动？
4. open() 如何最终进入驱动？
5. read / write / ioctl 分别解决什么问题？
6. 字符设备注册和设备节点创建是什么关系？
```

这不是考试题。它的作用是帮助读者在正式学习时知道应该把注意力放在哪里。

对于工程分析类文档，可以转换为"后续验证重点"，列出需要通过代码、编译、运行、测试或实验确认的问题。

---

## 十一、来源与引用规范

如果输出依赖网络研究或外部资料，关键技术事实必须能够追溯。

优先使用：官方文档、Linux Kernel Documentation、标准、RFC、官方项目文档、厂商官方文档、官方 API 文档。

其次才使用：高质量技术文章、大学课程、高质量教程、工程实践资料。

社区内容可用于发现常见问题、工程实践、容易产生误解的地方、官方资料覆盖不足的实际问题。

关键技术事实不能只依赖低权威来源。

### 正文引用

重要事实应在正文对应位置提供来源。不要只在文末堆积链接。

### 参考资料

文末可以提供 `## 参考资料`，只列最重要、最值得继续阅读的资料。不要堆积大量无关链接。

### 来源不是文章结构

禁止"文章 A → 总结 + 文章 B → 总结"的直接拼接。正确方式：多个来源 → 提取事实 → 交叉验证 → 建立模型 → 识别关系 → 重新组织 → 生成文档。

最终文档应该是重新组织后的知识结构，而不是搜索结果的拼盘。

---

## 十二、版本与时效信息

对于版本敏感的内容，应明确区分：

```text
通用原理
↓
主线实现
↓
特定版本
↓
特定发行版 / SDK / 厂商实现
```

涉及以下内容时尤其需要注意：Linux Kernel、API、驱动框架、软件库、编译工具链、协议实现、厂商 SDK。

如果用户指定版本，应优先围绕指定版本组织内容。如果未指定版本，优先描述通用原理，并提醒明显存在的版本差异。

不得把特定版本行为描述成永远成立的规律。

---

## 十三、图文、代码与结论一致性

最终文档必须进行三项一致性检查：

### 图文一致

图中的模块、关系、方向和正文描述必须一致。

### 代码一致

示例代码必须真正对应正文解释的概念。

### 结论一致

表格、流程图、代码、正文和最终结论不能互相矛盾。

如果发现不一致，应修改或删除有问题的表达，而不是保留所有内容强行解释。

---

## 十四、最终质量检查

在输出最终文档前，除 Markdown 格式检查外，还必须进行内容质量检查：

### A. 目标匹配度

当前文档是否真正服务于目标？如果不是，删除无关内容。

### B. 核心覆盖度

核心知识是否存在明显遗漏？如果存在，补充必要内容。

### C. 知识脉络

读者能否理解知识为什么连接在一起？如果不能，重新组织。

### D. 前置知识

是否出现大量没有解释的专业术语？如果有，补充最小必要背景。

### E. 图文一致

图里的结构和正文是否一致？如果不一致，修改。

### F. 代码一致

示例代码是否真正对应正文？如果不对应，修改或删除。

### G. 信息膨胀

是否因为获得大量资料，就把不必要内容全部塞进文档？如果是，删除。

### H. 准确性

关键技术事实是否可靠？如果存在冲突，检查版本、实现和来源。

### I. 独立可读

未来用户只打开这份 Markdown，是否仍然能够理解？如果不能，补充必要上下文。

---

## 十五、最终判断标准

输出前必须问自己：

> 如果读者只花 10～20 分钟阅读这份文档，能否对这个主题形成可靠的整体认知？

如果不能，优先改善：整体结构、知识关系、为什么存在、工作流程、示例、图示。而不是简单增加字数。

---

## 十六、最终输出原则

最终文档应该追求：

```text
匹配度 > 信息量
知识关系 > 知识堆积
理解 > 记忆
知识地图 > 百科全书
结构 > 堆砌
独立可读 > 对话依赖
```

最终目标是：

> **让输出文档成为一个独立、准确、可长期阅读、可继续扩展的知识载体。**
